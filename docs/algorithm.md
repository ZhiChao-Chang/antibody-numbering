# 算法结构

## 流程

1. 入口解析FASTA，检查字符，移除对齐横线，保留原始位置映射。
2. `AnchorNumberer.locate()`综合保守残基、长度约束与参考框架相似度，尝试候选分段，选择重链/轻链框架解释。
3. `framework_alignment()`使用本项目实现的Needleman–Wunsch动态规划建立框架残基对应关系；框架区读取参考标签完成映射。
4. 在定位的框架之间确定环区计算片段，`loop_labels()`根据链类型、κ/λ亚型、片段长度、体系及末端完整性计算标签。内部片段边界不等于每种体系的全部CDR定义。
5. 分别生成Kabat、Chothia、IMGT、Martin、AHo映射，记录无法识别和超出支持范围的情况。
6. 可选地按标准位置查询本地参考频率表；频率不参与编号选择。

## 参考框架

五个参考为6VJA VH/VL、6XDG的REGN10987 VL、1N8Z VH和2VIR VL。JSON包含框架序列、区段与五体系标签；环区序列替换为X、环区标签留空。它们是开发参考，不构成独立留出验证集。新序列按计算得到的匹配关系编号，不按名称、序列哈希或输入记录编号查找答案。

定位的比对分数是算法内部评分，未校准为概率。最高分候选只是现有规则下的选择，不保证生物学正确性。

## 支持范围与兼容行为

当前以单抗体可变域和已实现的常见H、κ/λ模式为主。长度限制及缺口规则在`engine.py`中显式定义；极端环长、特殊框架插入、多域串联或明显偏离参考的序列需要额外验证。部分规则支持端部截短，不代表任意片段都能可靠恢复编号。

部分19残基H2计算片段在旧版abYsis的AHo转换中仅返回前部标签。代码显式保留该兼容行为，在`compatibility_notes`中说明，其余位置可能留空；不能将此输出解释为完整的标准生物学编号。

`backend_outputs.json`的顶层状态与逐体系状态需要一起查看。`unsupported`保留原因；`unclassified`不能当作该蛋白必然不是抗体的证据。`manifest.json`中“需要审计”的阶段标记表示运行完成不等于独立验收完成。

## 参考频率

频率按指定体系、带H/L前缀的位置及氨基酸查询。值为公开计数除以包含gap的总数再乘100，参考物种范围为All。没有参考表、未知残基或没有映射位置时留空。频率缓存不会更新或下载，也不包含对新输入序列的查询答案。
